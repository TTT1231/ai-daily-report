# 供给来源模式：把用户给的混合素材直接做成日报

> 这是 `ai-daily-report` skill 的细节文件。主线在 [`../SKILL.md`](../SKILL.md)。

## 什么时候用

用户直接供给素材（而不是走 `rss:pick` 勾选），让 agent 理解素材并生产当期日报。输入可能是：

- 从本项目 RSS 候选池复制的对象（含顶层 64 位 hash、`sourceId`、`title`、`link`）；
- 外部 JSON 对象、单独 URL、完整 HTML 或粘贴文本；
- 本地文件；
- 只有一张图片、没有正文和外链的纯视觉素材。

一句话：**用户负责选定来源，agent 负责理解、取证、编排并生产**。每个 source unit 默认独立成一个 Story；按最多 5 个正文栏目归组，同栏目内部保持输入顺序。合并栏目不等于合并 Story；用户明确指定顺序或合并/拆分时遵从用户。取证失败的来源记录排除原因并跳过，不制作无证据 Story。

## 浏览前的确定性预检

不要靠对话中的心算统计来源，也不要写完完整 `data.json` 才发现导航过宽。开始浏览或下载证据前，在同一个 OS 临时工作区写一份 `sources.json`，然后运行：

```bash
bun run evidence:prepare-supplied --input <temp>/sources.json --output <temp>
```

输入格式：

```json
{
  "sources": [
    {"hash": "64位RSS哈希", "sourceId": "linuxdo-news", "title": "来源标题", "link": "https://..."}
  ],
  "storyPlan": [
    {"id": "topic-123", "sourceIndexes": [1], "topTitle": "模型产品", "bottomTitle": "短标签"}
  ]
}
```

- `sources` 按用户输入顺序逐项记录；外部 URL 写 `link`，粘贴 HTML/文本写 `content`，本地文件写绝对 `localPath`。未命中 state 的来源也保留为独立 source unit。`sourceIndexes` 为 1 基，可表达用户明确要求的合并或拆分。
- `storyPlan` 在取证前固定来源对应关系、ID 和导航标题，不编造事实。正文 `topTitle` 最多 5 类（不含概览、结语），同类连续；即使像素宽度足够也不放宽数量。采用同一分类层级，不混用公司、业务形式和技术类别，不为单条新闻新建栏目。预检同时拒绝未分配来源、重复 ID、非连续重复栏目、超额分类和宽度溢出。
- `manifest.navigation.top` 保留宽度与密度信息作为补充。`topComfortFillRatio` 是宽度软线，正文栏目数量上限由 `config/video-layout.json` 的 `maxTopCategories` 独立硬校验；缩短标签不能绕过数量限制。
- 命令按 hash → 规范化 link → LinuxDo topic ID 匹配 `rss-state.json`，批量下载候选，按 URL/内容哈希去重，并自动过滤可确定的头像、Logo 和小图标；默认并发 4，最多 8。
- 读取输出的 `manifest.json` 作为本次唯一来源/候选清单。只目视 `reviewable: true` 的不同文件；`filtered`、`failed` 不进视觉工具，`duplicate` 只看其 `duplicateOf` 指向的原图。复跑必须沿用同一临时目录以命中缓存。
- 预检失败时不下载候选、不打开网页；一次性修正 manifest 中同一类问题后重跑。`dense` 是软提示，不算失败。最终汇报的 source/story/candidate 数及导航占用率以 manifest 为准，不再手工估数。

## 输入路由：先查 state，不要见到 URL 就开浏览器

对每个 source unit 依次判定，**以 hash/link 是否命中 `ingest/rss-state.json` 为准**，不凭对象"看起来像不像 RSS"猜测：

```text
解析 source unit，提取 hash / sourceId / title / link / 嵌套 URL
→ 按 hash 查 ingest/rss-state.json
→ 未命中再按规范化 link（去参数、比 topic id）查 rss-state.json
→ 命中：走下方「RSS state 路径」
→ 未命中：当作外部来源，按需访问链接
```

- 对象来自 RSS 但本地 state 过期/缺失时，按 `sourceId` 查 `ingest/sources.jsonc` 刷新对应 RSS，而不是直接打开普通网页。
- 外部来源的网络抓取（代理、Cookie、UA）一律遵循 [`rss-pick-mode.md`](./rss-pick-mode.md) 的「抓取规则」：以 `sources.jsonc` 为单一事实源。

## RSS state 路径：不进帖子页面取图

`ingest/rss-state.json` 每条记录的 `description` 是 cooked HTML，通常已含帖子正文、`cdn3.ldstatic.com/original/...` 原图链接、optimized 链接和外部原文链接。**state 命中时**：

- 直接从 `description` 提取全部图片候选，优先 `/original/` 全尺寸链接，按 CDN 方式下载（代理 + UA + 原帖 Referer + 重试，见 `rss-pick-mode.md` 的 linux.do 示例）；
- **不要**再打开帖子页面，也**不要**重新请求 topic `.rss`——Linux.do 整站在 Cloudflare 后，绕开 state 去浏览帖子正是历史上撞 challenge 页的根因；
- 只有 state 不存在或确实需要刷新时才请求 RSS，且必须复用真实层的来源配置、代理、Cookie 和 UA 逻辑。

**先保留更正语义，再提取正文**：解析 cooked HTML、外部 HTML 或粘贴文本时，不得把格式标签全部抹平后再抽事实。`<s>` / `<del>` / `<strike>` 中的内容以及来源明确标注为撤回、勘误、已更正或「经核查无此内容」的主张一律记为 **retracted**，不得进入已确认事实；同一主张若仍被其它材料支持，则记为 **conflicted**，不能因为换了一个来源就自动恢复为确定事实。冲突只沿该主张定向核验最接近事实的一手材料；政策、标准、法律义务等规范性主张以官方正文或官方解读为准。仍无法解决时，只在冲突本身具有新闻价值时保留限定表述，否则省略。

**追链前先固定选题承诺**：用户提供的标题默认代表选择该 source unit 的角度，是待核验的选题意图而不是天然正确的事实；只有 URL、文件或图片时，则从其核心内容提炼。追链用于核验、纠错和补充这个角度，不得因为外部页面上另一个更醒目的标题、数字或配图而无声换题。原角度被证伪、撤回或必须实质改写时可以纠正，但要在下方内容与证据审计行中明确说明。

## 来源质量：论坛不总是中介，证据够了就停止追链

不存在"论坛一律舍弃"或"论坛一律采用"的固定规则，按帖子自身材料判断：

**高质量帖子本身就是直接来源。** 作者原创实测、技术分析、产品体验或事实整理类帖子，正文与附件共同构成一手材料；帖子正文可以直接支撑 Story，作者自己的分析不能在追外链时被无意丢掉（区分官方事实、作者实测、作者判断即可）。帖子含外链不等于帖子只是中介。

**论坛附件可以是一手证据（primary artifact）**：官方推文/公告截图、benchmark 与数据图、产品界面、更新日志、官方成绩图等。这类附件直接下载作为 overlay，不要截论坛页面周边，也不必为"来源更官方"换成说服力更差的官网首页截图。

**追链决策**：

```text
评估 RSS 正文 + 帖子原创内容 + 附件能否支撑全部 Tabs / Scenes / Subtitles 的核心主张
→ 足够：直接构建 Story，停止追链（发现过但未采用的外链只是参考线索，不进证据记录）
→ 不足：只沿与缺失事实相关的外链定向访问原文，不做无差别遍历
```

继续访问原文的典型情形：帖子只是转述新闻、附件只是封面/头像/Logo/媒体水印图、附件无法证明核心数字/日期/机制、Tabs 需要的事实只在外部原文里、RSS 完全没有图片只有外部文章链接。访问原文是为了事实核验或找更强证据，不是为了重新获取已存在的论坛附件。

**追链是例外不是默认，判据是证据说服力**：「能否支撑」不看「技术上有没有图」，看现有图证的说服力——帖子图片本身就是官方原文的截图（自带官方抬头/账号/站点标识）时说服力已经足够，不必再去原文找证据链；图证说服力弱（无来源标识的文字截图、与主张只有间接关系的泛化图、模糊不可读的截图）时，才沿外链定向找更强证据。经验上多数帖子属于前一种（先验约 6:4，不是配额）——评估从「帖子证据够不够强」出发，不从「要不要打开原文」出发。说服力只决定追不追链，不豁免核验：再强的截图，进入口播的数字与日期仍要走事实台账。

**文字截图不当事实源，当展示层**：候选里的原文文字截图（正文段落、摘要框等纯文字内容）原则上不承担事实核验——事实从帖子正文或外链原文文本获取；需要的事实只在文字截图里、且外链可访问时，定向拉原文文本核验（属于「事实核验」而非无差别遍历），不逐张深度读图抽取。文本比 OCR/逐图视觉理解快，也更可靠。拉到文本后，文字截图只做对齐级复核：确实出自此文、标题/段落对得上、未被裁改。图是图表/benchmark/产品界面/官方公告等一手材料，或没有可访问的外链原文时，图仍是事实源，照旧逐张目视。经验信号：多图且不带原文外链的论坛帖，附件大多是官方截取（官方公告/官方账号页面的直接截图）——这类图本身就是原文，没有可替换的原文文本，直接按一手材料逐张细读，不因无外链而降级为对齐复核或额外追链搜源。这条不豁免下文「候选遍历在先」：每个候选仍要枚举分类，只是文字截图类候选的事实依据来自文本而非视觉抽取；同理，下文「先查看完整原图并由原图核验事实」在此分流下的对应物是原文全文文本——文本承担核验，截图承担展示。

## overlayImg 是证据层，不是装饰图

- 每个 overlay 必须能证明对应 scene 字幕陈述的核心事实；只与主题存在联想关系的泛化配图（普通人物照、展会照、Logo 墙、气氛图）不满足证据要求，也不能靠「描述这张图本身」绕过。一张图片可以持续覆盖多段相关讲解，不一张图套多段不相关字幕，也不一条泛化字幕重复套多张图。
- 写任何依赖图片的口播或 Tab 前，必须先查看完整原图并由原图核验事实；overlay 可以使用比例和信息量合适的局部裁剪，但裁剪必须保留所述事实依赖的主体、来源、日期、数字和限定条件，禁止只看裁剪图就扩写出原图上下文里没有的更完整事实。完整原图承担核验，合格裁剪用于展示；长截图不作 overlay（见 [`images.md`](./images.md)）。
- 禁止用 agent 手搓标题卡、来源摘录卡或 AI 生成插图冒充原文证据。URL 获取失败不能转成手搓卡；纯文本输入也必须取得可核验的来源证据图片才能入选，不能自行绘制摘录卡兜底。
- 图片下载或截图后必须逐张目视检查：确认是预期内容、在 1920×1080 overlay 中可读、且真的支撑当前 scene。结构校验通过不能替代目视复核。

### 网页截图规范

外部网页取证时：

1. 等待页面稳定，确认不是 challenge、登录页、加载页或空白页；
2. 优先下载原始图表/产品图片；需要文字证据时才截图正文局部；
3. 优先元素截图或精确裁剪，不截整页/整视口；
4. 保留足够来源上下文（站点/机构名、标题、日期、核心事实段落），排除侧栏、广告、推荐区和无关导航；
5. 文字类证据截图（内容全是文字的正文/摘要截图）必须保留可辨认的来源标识：站名/logo、来源行、媒体署名至少其一——纯文字图没有出处，与手搓摘录卡无异。裁剪丢了标识先重截补入品牌带（站点标识 + 标题 + 来源/日期行 + 关键段落），确实截不到（反爬、来源图本身无标识）则弃用该图；核心证据无法替代时排除 Story。原始图表、benchmark 图、产品界面、官方公告截图的可信度来自内容本身，不适用本条；也不得为凑标识改截带侧栏/要闻栏的整页——无关内容在 overlay 里只是噪点；
6. 关闭遮挡式弹窗、Cookie 提示和悬浮广告，但不修改正文事实内容；
7. 广告嵌在核心段落且无法干净裁剪时，换官方图片、图表或另一可信来源，不强行凑数。

**外链取证预算**：先完成 manifest 中全部 state 候选的批量目视，只有某个 Story 的核心事实仍缺少可采用证据时才追链。独立页面在工具支持时最多 3 个并发加载，但每个页面仍单独核验来源与事实。一次页面操作应合并完成正文提取、challenge/登录态检查和目标元素定位；同一 URL 最多做 2 次截图尝试。第一次优先原始图片或元素截图；元素截图不可用时，第二次只截一个稳定视口并离线精确裁剪，不继续反复改 viewport、探测 DOM 或隐藏零散节点。两次仍不合格时，只允许切换到 manifest 已列出的另一个可信原文一次；仍失败就记录该 source unit 的排除原因并继续其它选题。页面已有明确进展且只剩一次确定性裁剪时可以完成该裁剪，但不能开启新的试错循环。

同一外链默认只保留一张最有说服力的最终证据；只有页面内确实存在由不同区域分别证明、且值得进入口播的多个独立核心事实时才保留多张。中间截图只放在 OS 临时工作区，不复制进 `data-scheme/images/`。

图片下载后、裁剪前运行 `bun run image:normalize-orientation -- <path>`，按 EXIF orientation 烘焙旋转并清除标记；若裁剪工具已经把像素转正却错误保留方向标记，则加 `--pixels-upright` 只清标记。Chromium 按残留 EXIF 旋转显示，而尺寸闸按像素宽高读取，两者错位会让图片横倒进成片——`bun run check-evidence` 会直接拒绝此类文件。

**必须拒收**：`Just a moment` / Cloudflare challenge /「正在进行安全验证」页、只有 Logo 或加载动画的中间态、登录/403/404、核心事实不可见、广告或推荐内容占主要区域、实际页面与预期来源不符、纯文字截图无可辨认来源标识且重截不可得（按第 5 条排除）。`bun run check-evidence` 会拦住"HTML 存成 .png"的错位文件，但真截图成的广告页/challenge 页只能靠上面的目视复核发现。

## 只有一张图片的来源

全部信息只在一张图、没有正文和外链时：这张图同时是内容来源和最终证据，不是"无来源"。

- 对原图做视觉理解或 OCR，只使用图中明确可见的标题、数字、日期、图表和结论构建 Story、Tabs 与 Subtitles；不能用常识补写图外事实。
- 原图比例正常、信息集中时直接作 overlay；图片很长或含多个独立区域时，可从同一原图做忠实裁剪分作多张证据，不得重排、改写或伪造。
- 图模糊到无法可靠读取时，报告来源不可用并跳过，不用自制卡片掩盖识别失败。

## Story 复杂度随来源伸缩，无固定配额

- **整条音频必须独立讲清选题**：全部 subtitle 连起来必须解释 contentTitle 的核心事件及决定新闻价值的具体事实。标题里的关键关系、数字、期限不能只放在 Tabs。先寻找能覆盖这些核心事实的证据；核心证据仍不足则排除整条 Story，不能只留下边缘事实凑一条新闻。
- Tabs 2–6 张、Scenes 1–6 段（Schema 上限），数量由核心主题、可证事实、图片信息增量、可读性和视频时长共同决定；来源丰富只提供更多选择，不等于全部采用。
- **候选遍历在先，禁止找到第一张就停**：先由 `evidence:prepare-supplied` 枚举 state 候选、去重并机械排噪；agent 只批量目视 manifest 中 `reviewable: true` 的不同原图。每张得到一个结果：**采用 / 重复 / 次要 / 不可读或长截图 / 不能直接证明相关事实**。全部可审候选分类完成前不得写 Scene；落盘资产只有第一张图及其裁剪变体时必须回查候选台账，只有其它候选均有明确舍弃理由才可继续。
- **内容与证据审计检查点（不中断执行）**：写 Raw 前，在 commentary 为每个 source unit 输出一条紧凑审计行，合并记录「选题承诺、计划进入口播的核心、retracted/conflicted 状态与处理、图片候选总数、采用图片及其独立事实、舍弃数量与理由」。它不是向用户申请确认，输出后继续生产；目的是同时让编辑选择、事实状态和逐图检查可审计，不再另设第二套输出仪式。若所有 Story 最终都只有一个 Scene，而任一来源存在多个独立且值得口播的图证事实，视为新的固定模板，必须返回台账重做。
- **最少充分证据集**：覆盖选定核心事实的最少不同证据图，最多 5 张。每段口播必须有对应的来源图片，不能以“同一篇文章”代替图内事实匹配。完整原文用于核验，展示图必须保留该段所需事实和限定条件。
- **证据与口播可一对多**：一张图可以对应多个连续 Scene，逐段显式填写相同 `overlayImg`，所有字幕都必须由这张图支撑。同图跨句保持相同 scale，避免重入或跳动；事实转移才换图。不同证据最多 5 张，Scene 总数仍为 1–6；禁止复制文件换路径来绕过限制。
- **按理解所需安排讲解**：取消统一 5–8 秒和 45 视觉单位上限；subtitle 仍遵守 Schema 的 96 字上限，较长讲解可以分成多个同图 Scene。根据图片信息量解释关键事实、比较对象及结论，不能只念一句标题就切走。简单公告可以短，密集图表需更长观察与解释时间；不靠空话、重复句或统一慢速拉长。TTS 后按同一证据连续展示的总时长复核，不要求每张图达到固定秒数。
- **正文全程以证据为主**：禁止在证据之间、结尾或开头插入无图段帮助读卡。Tabs 留作结构化编辑摘要，不再安排整屏读卡时段；总结仍在对应证据上完成。
- **无证据则不入选**：先补取核心事实的对应证据；可选细节找不到可用证据则不进入口播，核心事件无法覆盖则排除整条 Story并记录原因。不得自动继承上一张不相关图片、使用装饰图或自制文字卡掩盖缺证据。
- 也不能反向压缩：不为省 TTS 或赶流程牺牲丰富来源应有的证据层次，不把多张证据硬塞一张合成图。

## Tabs 质量

Tabs 是对单一主题的完整阐述，不是大纲。硬约束不变：2–6 张（Schema 范围）、每张 25–80 可见字符、完整事实句、一段粗体突出核心。写作纪律与真实层 `ingest/prompts.go` 同源，按 supplied 输入改写如下：

- 写作前先识别互不重复的独立事实；Tab 数由采用的独立事实簇决定，不按正文段落数机械映射，也不向 Schema 下限滑移。
- 2 Tabs 只适合确实只有两个有价值、互不重复事实角度的薄来源；来源有 3 个以上重要独立事实时，通常应生成 3 张以上 Tabs。可以取舍次要事实，但不得用泛化影响替代被遗漏的明确事实。
- 各 Tab 合起来形成连贯解释顺序：背景与发生了什么 → 核心证据与数据 → 机制/产品细节 → 来源明确表达的影响与限制。
- `contentTitle` 概括核心结论；口播必须让不看 Tabs 的观众听懂核心事件与至少一个决定其新闻价值的具体事实；Tabs 展开证据、机制和上下文。三处允许语义重叠，只禁止逐字复读。
- 不得补来源中没有出现的日期、价格、功能、修复状态、政策、长期规则、建议或结论；不确定性只能作为具体事实的限定词（如「尚未确认」），不单独成卡、不放在口播结尾。
- 自查标准：把任何一张 Tab 整条删掉，观众都应少知道一件具体的事，否则该 Tab 不合格；空泛免责卡（「细节待确认」「以官方为准」「温馨提示」）等于零信息，禁止生成。
- 图片证据中不确定的内容要保留事实状态（「尚未确认」），但不使用「据截图显示」这类媒介指涉模板。
- 来源单薄时可以只做 2 张克制的卡；两轮定向整理仍凑不出两个互不重复的事实角度就跳过该 Story，不编造。

## 事实台账：先提取、后编排

写 `data.json` 前，对每个 source unit 在一轮推理内完成事实台账。这是内部流程纪律：不新增任何 `data.json` 字段，也不生成长篇追链日志。

```text
1. 记录待核验的选题承诺，再列出互不重复的独立事实。
2. 为每条事实标记出处：正文 / 完整原图 / 外部原文。
3. 区分：已确认事实 / 来源明确表达的影响 / 不确定信息 / retracted / conflicted。
4. 对 retracted 直接排除；对 conflicted 按上文规则定向核验，未解决则限定或省略。
5. 记录采用或舍弃，按采用的事实簇确定目标 Tab 数（见上文 Tabs 质量）。
6. 先规划整条口播如何兑现选题承诺，再规划 Tab 与各 Scene 的事实和图片映射。
7. 写后逐句回查：contentTitle、每张 Tab、每段 subtitle 都必须能回到台账事实；全部 subtitle 联合起来还必须满足「整条音频独立讲清选题」。
8. 输出上文「内容与证据审计检查点」，并检查 Scene 数量分布是否又退化成整期固定一段。
```

禁止跳过台账直接写 JSON——整期统一滑向 2 Tabs、末段补评价建议、把泛化配图当证据，都源自没有先建立事实清单。

## 标题与口播编辑底线

- `introTitle` / `contentTitle` 是编辑标题，不复制来源标题：去掉论坛前缀、括号补注、标题党问句、情绪化措辞、冗余标点和来源名，保留核心主体、事件及真正决定新闻价值的数字或期限；润色不得改变已核验的选题承诺。两者都读起来像成品新闻标题。
- 口播与 Tabs 用直接、面向大众的短视频新闻语气；不提摄取平台、用户输入和生成过程，也不出现「贴文称」「据标题」「以官方为准」类措辞。有图 Scene 直接播报事实，不描述「截图、图片、画面、配图」这个媒介本身——图只限制能说什么，不决定怎么说。
- 优先以实施动作、发布政策或产出数据的新闻行为方作为事实主语；需要交代信息来源时，可以用「彭博社报道」「研究团队发现」「楼主实测」等明确报道方或观察者作归因。不要用「消息称」「消息指」「更新说明称」等匿名主体，也不得把仅承载证据的网页、平台或聚合站写成新闻行为方。
- 不以待披露信息收尾：未知信息只有在实质影响新闻时，作为限定词并入某张事实 Tab，不单独成卡、不放在口播结尾。

## 关键词替换底线

成片内容（标题、Tabs、口播、元数据、评论、SVG 可见文本）不得出现精确子串 `中国`，写入 Raw 前改写：

- 国内市场/公司/用户/团队/行业等语境用 `国内`；
- 国家作为主语或强调归属时用 `我国`；
- 政策、标准、战略、机构等国家层面概念用 `国家`；
- 直接替换会不通顺的官方名称或引文做语义改写，不因来源里出现过就保留原词。

不改动外部来源本身。渲染前扫描，任何命中都视为阻断性失败：

```bash
rg -n --glob '*.json' --glob '*.txt' --glob '*.svg' '中国' data-scheme
```

## 生产流程

```bash
bun run archive                    # data-scheme/ 里有上一期时先归档
# 在 OS 临时目录写 sources.json，先验证来源/Story/导航并批量准备 state 候选
bun run evidence:prepare-supplied --input <temp>/sources.json --output <temp>
# 写 data-scheme/data.json + 下载证据图到 data-scheme/images/
bun run check-data-json --strict-tone
bun run check-evidence --require-overlay
bun run tts
bun run generate-svg               # 或由多模态调用方（如 vision-generate-video）直接编写 SVG 后跳过本步：
                                   # 纯文本模型下 generate-svg 与 MCP 识图都慢，多模态直出更快
bun run check-icons
bun run check-data-json:render
bun run render:mp4
bun run evidence:frames             # 输出 manifest.json + 全部为 pending 的 review.json
# 逐帧填写 review.json 后；任何 pending/false 或过期哈希都会失败
bun run check-evidence-review -- --manifest=<temp>/manifest.json
```

- `check-data-json --strict-tone` 是 supplied 专用口吻闸：媒介叙述（「截图显示」「配图展示」等）直接失败；匿名归因与评价/建议/免责填空输出警告但不阻断。原生 RSS 与手动流程不带该 flag，不受影响；
- 每条证据图下载/截图后、进 `overlayImg` 前，先目视复核（见上文拒收清单）；
- `check-evidence --require-overlay` 是自动闸：正文任一 Scene 缺证据、文件缺失、HTML 冒充图片、尺寸不可读都会失败（默认模式同样严格）；自动闸过了仍要目视确认内容相关性；
- 最终视觉闸必须 fail-closed：`evidence:frames` 生成的 `review.json` 默认全部待审；逐帧确认方向、成片可读性、对口播事实的直接支持、来源可辨和无遮挡后才改为 `true`。广告、推荐位、Cookie 弹窗、登录/邮件墙、challenge 或无关 UI 任一遮挡均为 `false`，必须写明原因并修复后重新渲染、重新抽帧；禁止在同一份审核里直接把失败改成通过。只有 `check-evidence-review` 对当前 MP4、当前 Generated 数据和当前帧哈希全部通过后才能结束任务并删除临时帧目录；
- 来源确实无法取证时，记录 source unit、排除原因和缺失的核心事实，跳过这条 Story 并继续其它已取证选题；全部来源均被排除时停止，保留原数据包。不要把取证失败转成无图新闻。
- 完整 Raw 尽量一次写入；校验返回多处同类错误时，在一次文件编辑中批量修完该类后再复检，不按字段做几十次串行编辑。预检已经确认过的 Story 对应关系和导航计划不得在 Raw 阶段无故重算。
- 汇报 `manifest.json` 的预检/候选准备耗时，并记录外链取证、Raw 校验、TTS、SVG、渲染五个阶段的墙钟耗时；阶段没有发生时不补零。这样下一次性能回归能直接定位，不再用整轮总时长猜测。

## 与其它模式的关系

- 与 [`rss-pick-mode.md`](./rss-pick-mode.md) 的区别：那边读 `picks.json` 走原生 ingest；这边由 agent 直接理解素材写 `data.json`，但来源判定、抓取代理、证据与 Tabs 质量规则完全共享本文与真实层约束。
- 与 [`manual-mode.md`](./manual-mode.md) 的关系：数据结构与校验同手册；本文件额外约束来源路由、证据质量与 Story 伸缩。
- 本模式的图片理解与 SVG 生产由调用它的 agent 能力决定：多模态 agent（如 Codex）直接读图、直写 SVG；纯文本 agent 走 `CLAUDE_VISION_ENABLED` 视觉流程与 `bun run generate-svg`，慢但结果同规。
- 不跑 `bun run video:auto-generate` / `bun run video:half-auto`：它们会重抓并覆盖 `data.json`。
