# 成品新闻文案：让观众听一遍就明白

适用于全部生产入口的标题、`scenes[].subtitle` 和 `tabs[].summary`。**口播是完整的新闻讲述，Tabs 是补充阅读，图片是事实证据。** 观众不应靠读卡片、辨认截图或自行解释术语，才能知道这条新闻的重点。原生 RSS 的对应要求维护在 `ingest/prompts.go`。

## 先作编辑选择，再写 JSON

在同一次生成中完成以下编辑工作，直接交付成稿，不默认增加第二轮模型编辑或另建台账。supplied-source 的既有成稿审查合并事实与表达判断，不因口吻再开一次模型请求。原生 RSS 合格稿一次生成即放行，只有明确检查失败的 Story 才进入既有定向重试：

1. **选出值得记住的事**：沿用事实台账，先用一句话回答「这条最值得观众记住什么」。从原始选题和来源里挑出支撑它的核心事实，区分讲清事件必需的内容与可选补充。产品发布优先讲实际变化或用法；研究优先讲发现和成立条件；规则优先讲对谁、怎么变。不要把最醒目的数字、最容易截到的句子自动当成重点。
2. **先写完整口播**：暂不填 Tabs、不考虑 Scene 数，面向没读过来源的观众连贯讲述。开头直接给最有价值的事件或变化，后句接着解释它。每句应增加一件具体的事，或解释前句里必要的概念与关系；「面向希望参与研究的候选人」「扩展相关能力」等同义重述删去，换成来源支持的项目时长、用法、对象或结果。理解需要时自然解释技术含义，来源不支持的用途和因果不补写。
3. **按新闻价值分配篇幅**：简单公告可以很短；涉及机制、规则或比较的新闻给足讲解。不要让整期每条都成为相近长度的「标题一句＋边界一句」，也不要为了制造长短差异强拆 Scene。主次体现在选了哪些事实、讲述顺序和解释篇幅，不靠「重磅、炸裂」或每条固定补一句影响来制造。
4. **再安排展示**：按口播关系划分 Scene，匹配能够证明当前内容的证据，再整理 Tabs。核心事件、决定新闻价值的变化以及理解它必需的条件必须讲进口播；只有可选细节可以留在 Tabs。每段 96 字是分段上限，不是整条新闻的篇幅目标；同图可以支持多个连续 Scene。口播与摘要都没有凑字数的下限，完整短事实直接讲完，不用来源前缀、同义重述或免责句补长度；复杂事件仍须讲清核心，不能把取消字数下限理解为一律缩短。
5. **只听成稿，再对照来源**：忽略标题、Tabs 和图，读完一条全部 subtitle，用自己的话复述听到的事件与关键变化。复述不出来、只记住专名和数字、需要去卡片补核心内容，或整段都在解释「不能理解成什么」，就返回重写。最后对照原始选题与事实台账检查数字、归因、条件及新增主张，不能把标题改窄来掩盖漏讲。

把上述编辑判断记录在已有审核中：supplied-source 的 `narration` 记录听众应记住的一句话、不可遗漏的 `coreFactIds` 和整条口播判断；原生 RSS 的 `narration_review` 返回当前成稿核心事实及其实际口播原句。引用存在只证明有对应文字，不能拿审核字段自证自然；讲清核心、去掉无用转述与核对来源必须在本次生成完成。

## 用动词讲事件，用条件保留准确性

**默认直接讲新闻，按必要性保留归因。** 先找句子里真正做事的人、发生变化的产品或受规则影响的用户，再写动作和内容。公司调整自己的产品时，直接说发布、加入、接入、开放、调整了什么；介绍项目时直接解释它是什么、怎么工作；用户权益直接说谁能获得什么、条件是什么。不要把「称」换成「表示、指出、补充说明、描述为」后继续保留同一个空前缀。

来源可查与口播归因是两件事。每项事实都必须有证据，但不意味着每句话都要报一次媒体、公司或仓库。逐句判断：删掉这个归因，会不会把预测说成已发生，把个人自述、厂商自测或指控说成独立证实？会改变事实状态时，留下最短、明确的一层，如「IDC预计」「创作者介绍，自己……」「在厂商自测中」「州方指控」；否则把出处放回台账和证据图。不要仅因为材料来自媒体，就机械加「某媒体报道」。媒体独家获悉等来源身份本身影响可信度时，可以保留一次明确媒体归因。

不叠加「媒体报道，创作者称」「官方补充说明」「仓库将它描述为，并称」等转述层。保留真正需要承担这句话的人或测试条件，把内容直接接上去。同一事件后句继续讲内容，不再重报来源。媒体不是被报道的创作者，不能把「Kotaku报道一位创作者」压成「Kotaku创作者」。否认、反驳、更正或命名本身就是新闻时，直接说谁否认、纠正或命名了什么，保留必要来源关系。

准确性优先通过句子本身表达：「逐步开放」「仅在该平台内免费」「公开预览」「计划年底推出」「可能影响」「在某项测试中」。预测直接写「谁预计，何时可能发生什么」，观点直接讲谁认为的具体内容；不要写「2029年供需走向属于行业预测」这种给句子分类、却没讲出预测的审核话。保留会改变事实真假的人群、时间、口径、实验条件和例外。不要给每条加「这是他的判断，不是定论」「这不是彻底解决保证」「报道没有显示」「不是某人原话」等审核尾巴；误引更正本身有新闻价值时，直接讲更正内容。未采用主张与缺证原因留在台账，不给观众朗读检索失败。不能以润色为由把传闻写成确认、目标写成结果、加入目录写成已经可用。

来源里的准确性约束不是另一件要播出的事实。「财长预计……。行业分析另预计……」已保留两项预测的真实归属，不再追加「两项预测来自不同发言方」「后者不是财长原话」。同样，自述、测试与适用条件在事实句中交代一次即可，不在句尾再次给事实贴类别标签。

出处、原文位置与查证过程留在事实台账。口播和 Tabs 都直接组织事件及事实关系，不朗读「页面说明」「图表中写着」「帖子给出的日期」。文档修改、账号发言或榜单更新本身有新闻价值时，可以照实讲这些事件。

## 讲清关系，降低听觉负担

- 每句承接前句，不把接入、成绩、折扣和条款用分号挤成清单。先让观众知道数字衡量什么，再讲必要数值和比较条件；不穷举不影响理解的型号和小数。
- 使用自然普通话。通用英文描述准确译成中文，必要品牌、版本和单位保留；不自造音译，不把代码路径、音标或 Markdown 写进口播。
- 评测交代谁的哪项任务、结果与比较条件；单项成绩不扩成整体领先，误差区间重叠不写成明确超越。测试标签转换成「未启用工具」「样本量为400」等自然表达。
- 期限只按来源已确认的时间表达。原帖「未来三天」不等于播出日起三天，不擅自换算截止日。

## 完成标准

一条合格稿应能让只听声音的观众复述核心事件和关键内容，后句解释前句，必要条件自然出现。每张 Tab 都应提供具体信息，不用「言论边界」「使用边界」「观点边界」这类只有免责解释的卡片凑下限；确有重要许可、配置或适用范围时，直接用具体主题命名并讲规则。

逐句再问一次：这句话是在讲事件和内容，还是在报告「谁怎样描述这段材料」？每个归因都要有保留理由，不能以「来源可查」为理由例行念出。先删无用的转述层，再核对剩下的句子没有改变行为方、确定程度或适用条件。`naturalSpoken` 不接受只因语法通顺、出处准确就通过。

结构校验、关键词扫描、证据对应和 `--strict-tone` 都不能代替这项编辑判断。原生 RSS 和通用 Raw 校验（含直接 TTS）对明确的归类尾句、仓库代述、转述叠层与产品规则前缀执行相同的句式拒收，不依赖调用方记住额外 flag；`--strict-tone` 继续补充 supplied-source 的媒介叙述检查。命中时重写完整事实句，不自动删词，也不以换一个发言动词过关。其它「称」仍按上下文判断，不误伤「称为、简称」、有价值的引语或争议报道。只要仍需观众自行拼接核心信息，就继续改稿。
